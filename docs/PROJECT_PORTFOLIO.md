# 제주 POI 데이터 구축과 운영 상태 자동화 프로젝트

## 한 줄 소개

서로 다른 공공·지도·관광 원천의 제주 POI 데이터를 통합하고, 실제 운영 여부를 보수적으로 판정해 Airflow로 반복 실행 가능한 서비스 업로드 파이프라인으로 구축했다.

## 문제 정의

원천마다 장소명, 주소, 좌표, 카테고리, 운영 상태의 형식이 달랐다. 특히 지도 검색 결과가 없다는 사실은 실제 폐업과 다르지만, 이를 잘못 처리하면 정상 장소를 서비스에서 삭제하는 고위험 오류가 발생한다. 따라서 원본 행을 보존하면서 서비스 대상, 확인 필요 대상, 폐업 대상과 판정 근거를 분리하는 것을 목표로 했다.

## 데이터 수집과 통합

- 제주데이터허브·공공데이터포털·지자체 공개 데이터
- 행정안전부 LOCALDATA 인허가·폐업 원천
- 소상공인시장진흥공단 상가 정보
- 한국환경공단 전기차 충전소, 오피넷과 석유판매업 데이터
- VisitJeju 관광 API
- Kakao Local API의 장소명·주소·좌표·전화번호 보강 결과

출처별 스키마를 공통 POI 형식으로 바꾸고, 주소만 있는 행에는 좌표를, 좌표만 있는 행에는 가능한 주소를 보강했다. 좌표계가 다른 원천은 WGS84로 변환해 거리 비교가 가능하도록 정리했다.

## 데이터 품질과 의사결정 변화

### 카테고리와 중복

태그만으로 분류했을 때 음식점·둘레길 등이 교통시설로 잘못 들어가는 문제가 있어 장소명, 콘텐츠, 업종을 함께 읽는 방식으로 교정했다. 같은 주소라고 해서 중복으로 제거하지 않았으며, 한 건물 안의 식당·ATM·주차장·화장실·숙박시설이나 지점이 다른 체인점은 별도로 보존했다.

전기차충전소·공중화장실은 공식 원천과 주소·좌표를 다시 비교했다. 이름이 같아도 실제 위치가 다르면 유지하고, 명백한 중복만 정리했다. 시설 기능과 카테고리가 충돌하는 사례도 별도 QA로 점검했다.

### 상태 판정

초기에는 카카오 미발견을 강한 부정 신호로 볼 위험이 있었다. 재검토 결과 브랜드·법인·지점 표기 차이, 지도 검색 인덱스, 주소 표기 차이 때문에 실제 운영 장소도 빠질 수 있음을 확인했다. 이에 아래 정책을 고정했다.

1. 행정 원천에 명시적인 폐업 근거가 있을 때만 폐업 처리한다.
2. 카카오 미발견은 확인 필요로 남긴다.
3. 행정 원천 후보가 여러 개라 동일 장소를 확정하지 못하면 확인 필요로 남긴다.
4. 고정 공공·인프라 시설은 변경 근거가 없으면 운영으로 유지한다.
5. 이름이 비슷해도 ATM·충전소·주차장·세차장·화장실처럼 역할이 다르면 같은 장소로 매칭하지 않는다.

## 검색 최적화

편의점 등 체인 업종은 브랜드, 법인명, 지점명, 업종 접미사와 공백·기호 차이를 정규화해 검색 후보를 확장했다. 후보 인정에는 이름 유사도만 쓰지 않고 주소와 장소 역할을 함께 확인했다.

이 재검색으로 기존 카카오 미발견 서비스 유지 6,066건 중 750건을 해소했다. 다만 역할이 다른 장소를 정상 매장으로 오인할 수 있는 후보는 성과로 계산하지 않고 차단했다.

## Airflow 운영화

`jeju_poi_lifecycle_weekly_v10` DAG에 다음 단계를 분리했다.

| 단계 | 역할 |
|---|---|
| validate | 원본 CSV와 필수 경로·컬럼 검사 |
| preprocess_new_delivery | 이전 마스터 대비 신규·변경·유지 행 구분 |
| prepare | 판정 입력과 작업 디렉터리 준비 |
| prepare_kakao_checks | 재검색 큐 생성 |
| refresh_kakao_evidence | 카카오 증거 갱신 |
| classify | 행정·카카오 근거와 정책을 결합한 상태 판정 |
| export | 서비스용·전체 상태·판정보존 파일 생성 |
| quality_gate / report | 상태값, 행 수, 서비스 포함 조건, 폐업 근거 검사 |

입력 파일 형식이나 증거 경로가 틀리면 결과를 조용히 만들지 않고 DAG를 실패시켜 문제를 드러내도록 했다.

## 최종 출력

| 파일 | 구성 | 용도 |
|---|---|---|
| `제주_POI_서비스용_KEEP_current.csv` | 원본 양식, 영업·운영만 | 서비스 업로드 |
| `제주_POI_최종통합본_상태_current.csv` | 원본 양식 + `operating_status` | 전체 상태 확인 |
| `제주_POI_판정보존_current.csv` | 8개 최소 추적 열 | 상태·근거 보존 |

판정보존 목록은 `place_id`, `name`, `road_address`, `operating_status`, `status_reason_code`, `verification_state`, `lifecycle_type`, `place_key`만 포함해 서비스 데이터에 내부 열을 섞지 않도록 했다.

## 이 프로젝트에서 보여 주는 역량

- 이질적 공공 CSV·API·지도 데이터를 공통 스키마로 통합하는 데이터 엔지니어링
- 이름 유사도, 주소, 시설 역할, 행정 상태를 결합하는 다중 근거 매칭 설계
- 불확실한 결과를 강제 자동화하지 않고 확인 필요 상태로 보존하는 데이터 품질·리스크 관리
- Airflow 기반 입력 검증, 증거 갱신, 분류, 품질 게이트, 재현 가능한 출력 설계
- 서비스용 데이터와 감사·근거 데이터를 분리하는 실무형 산출물 설계

## 다음 개선 방향

확인 필요 5,675건은 오류 행이 아니라 추가 근거가 필요한 작업 큐다. 행정 원천의 갱신 주기를 관리하고, 신규·변경 POI만 증분 재검색하며, 수동 검토 결과를 이름·주소 정규화 규칙으로 다시 반영하면 검토량을 점차 줄일 수 있다.
