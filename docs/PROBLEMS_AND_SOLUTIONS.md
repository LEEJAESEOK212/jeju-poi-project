# 제주 POI 프로젝트 문제 해결 기록

이 문서는 제주 POI 프로젝트에서 실제로 확인한 문제, 원인, 선택한 해결책과 검증 범위를 한 장에 정리한다. 완료 수치와 실험·보류 과제를 섞지 않는다. 상세 작업 이력은 [추가 수집 기록](POI_COLLECTION_UPDATE_20260928.md), 운영 상태 설계는 [기존 포트폴리오](PROJECT_PORTFOLIO.md), 최근 통신 개선의 계산 근거는 [통신 개선 사례](HTTP_CONCURRENCY_CASE_STUDY.md)에 있다.

## 전체 흐름

```text
이질적 원천 수집
  → 공통 스키마 변환
  → 주소·좌표·카테고리 보강
  → 이름·주소·좌표·장소 역할로 중복 검증
  → 운영 상태와 콘텐츠 근거를 별도 관리
  → 품질 게이트와 재개 가능한 실행으로 배포
```

## 핵심 문제와 해결

| 문제 | 왜 문제가 됐나 | 해결 | 확인한 결과와 범위 |
|---|---|---|---|
| 원천마다 필드와 좌표 형식이 다름 | 이름만으로는 같은 장소인지, 위치가 맞는지 비교할 수 없었다. | 공통 POI 스키마로 변환하고 도로명·지번을 분리했다. 좌표계는 WGS84로 맞추고, 주소만 있는 행은 정방향 지오코딩, 좌표만 있는 행은 역조회 대상으로 분리했다. | 지도 거리 비교와 원천 간 대조가 가능해졌다. 주소나 좌표가 없다는 이유로 인근 주소를 대신 입력하지는 않았다. |
| 동명·동주소 시설을 단순 중복으로 삭제할 위험 | 한 건물 안에 매장, ATM, AED, 화장실, 주차장, 충전소가 공존할 수 있고 지점명도 다르다. | 이름 정규화, 도로명·지번, Haversine 거리, 전화번호, 카테고리와 장소 역할을 함께 사용했다. 같은 주소만으로 합치지 않고 근접·유사 후보는 검토표로 분리했다. | 명백한 중복만 정리하고 별도 기능의 부속시설은 보존했다. 거리 임계값은 실측 정확도가 아닌 후보 선별용 운영 기준이다. |
| 주소 표기 차이로 공식 매칭이 누락 | 건물명·동·층·괄호가 붙은 주소는 같은 시설인데 전체 문자열 비교에서 탈락했다. | 정확한 상호명이 먼저 일치할 때만 도로명+건물번호 또는 법정동+지번을 다시 비교했다. | 행정 매칭 not_found가 12,434건에서 11,914건으로 520건 감소했다. 새 폐업 후보 37건은 자동 반영하지 않고 검토 대상으로 남겼다. |
| 주소와 좌표가 충돌 | 역지오코딩 결과가 원본 주소와 달라 원본의 장소 정체성을 훼손할 수 있었다. | 원본 주소를 우선하고 그 주소를 다시 정방향 지오코딩해 좌표·도로명을 확인했다. 여러 후보 또는 불일치 결과는 자동 반영하지 않았다. | 도로명만 또는 지번만 존재하는 경우도 별도 보존했다. 건물번호가 없는 버스정류소 같은 장소는 주소 공백이 정상일 수 있다. |
| 카테고리 자동 분류 오류 | 태그만으로 분류하면 음식점·둘레길 등이 교통시설 등으로 잘못 이동했다. | 장소명, 콘텐츠, 업종, 시설 기능을 함께 검토해 확실한 사례만 이동했다. 공방은 기존 정책대로 교육시설의 체험학습장으로 통일했다. | 초기 정제에서 보수적 규칙으로 214건을 재분류했다. 신규 카테고리는 통합 전에 ID 표와 차트부터 갱신했다. |
| 공공 원천의 정보는 신뢰도가 높지만 장소 설명이 부족 | 실제 방문 판단에 필요한 설치 위치, 이용 시간, 기기 정보 등이 분산돼 있었다. | 원천의 사실만 콘텐츠와 태그에 보강했다. AED는 설치 위치·이용 가능 시간·기기 정보를 중복 없이 자연어로 정리했다. | AED 원천 1,353건 중 완전 중복 1건을 제외해 1,352건을 추가했다. 출처는 전국자동심장충격기표준데이터로 명시했다. |
| 원천 행 수를 신규 POI 성과로 오인할 위험 | 같은 장소가 기존 마스터에 이미 있거나 행사·기사처럼 상설 POI가 아닐 수 있다. | 원천 건수, 중복 후보, 확정 신규, 정보 보강을 분리해 기록했다. VisitJeju 후보도 이름·주소·좌표 대조 후 신규 후보와 검토 후보를 나눴다. | VisitJeju 관광지 1,311건 중 반경 150m 내 일치 없음 244건은 확정 추가가 아닌 신규 후보로 남겼다. |
| 지도 검색 미발견을 폐업으로 처리할 위험 | 지도 색인 누락, 법인명·지점명 차이, 데이터 갱신 차이로 정상 장소를 삭제할 수 있다. | 행정 원천의 명시적 폐업만 자동 폐업으로 처리했다. 미검색·다중 후보·근거 부족은 확인 필요로 보존했다. | 기존 운영 상태 기준 57,989건에서 폐업 1,582건은 명시적 행정 근거를 가진 경우만으로 기록했다. |
| 영업장 규칙을 고정시설에 적용하는 오류 | 충전소, 화장실, 자연·문화 시설은 일반 사업장과 생명주기가 다르다. | 먼저 시설 유형별 생명주기 정책을 적용하고, 영업장에만 행정·지도 확인 흐름을 적용했다. | EV 충전소, 공중화장실, ATM 등은 역할이 다른 모시설과 매칭하지 않도록 예외를 명시했다. |
| 공개 파일에 내부 판정값과 사용자용 상태가 섞임 | KEEP/DEACTIVATE만으로는 파일 사용자가 의미를 바로 알기 어렵다. | 서비스용, 전체 상태, 판정보존 파일을 분리하고 공개 상태는 영업·폐업·운영·비운영·확인 필요로 제한했다. | 서비스용 파일에는 영업·운영만 포함되는지, 상태값과 행 수가 맞는지 품질 게이트로 검사했다. |
| 대량 콘텐츠 생성에서 일반 문장이 반복되고 사실을 과장 | 장소명·카테고리만으로 만든 설명은 실제 특성이 없고 환각 위험이 컸다. | SEARCH → FACTS → GENERATE로 분리했다. 확인된 원문 근거가 없으면 생성하지 않고, 콘텐츠는 확인된 사실의 편집·요약만 하도록 했다. | 초기 템플릿형 보강은 최종 콘텐츠 성과에서 제외했다. 정보가 적으면 짧게 쓰거나 보류한다. |
| 검색 결과가 다른 지점·주변 장소 정보를 섞음 | 여행 종합 페이지와 디렉터리는 현재 POI가 아닌 정보를 함께 담을 수 있다. | 상호와 주소가 가까운 문맥에 함께 있는지 확인하고, 후보 URL·본문·사실을 분리해 저장했다. | 자동 `본문근거확보`는 장소 동일성 신호일 뿐 최신 정보 또는 최종 콘텐츠 승인으로 취급하지 않는다. |
| 직접 플레이스 상세 수집의 차단과 약관 위험 | 차단 우회는 안정성·운영성·정책 측면에서 적합하지 않았다. | 직접 플레이스 수집을 중단하고 API HUB 검색 결과와 접근 가능한 공개 본문만 사용했다. robots 규칙, 도메인·사설주소 차단, 요청 간격을 수집기에 넣었다. | 검색 API는 URL 발견 도구로 사용하고, 검색 요약만으로 사실을 확정하지 않는 규칙을 유지했다. |
| Common Crawl·Instagram 등 대체 소스의 낮은 효율 | URL을 모르는 소규모 제주 업체를 대량으로 찾는 용도에는 적중률과 운영 비용이 불확실했다. | Common Crawl은 전체 POI 동시 탐색 방식까지 시험했지만 주력 경로로 확정하지 않았고, Instagram 직접 수집도 주력에서 제외했다. | 기술적으로 가능한 방식과 실제 운영 가능한 방식을 분리해 기록했다. 현재는 공식 원천 우선, 부족분은 검색 API 기반 후보 탐색을 사용한다. |
| 장시간 실행이 중단되면 같은 API 호출을 반복 | 수집 중 네트워크 오류나 사용자 중단이 나면 비용과 시간이 다시 든다. | 검색 캐시, 본문 캐시, 완료 결과를 SQLite 체크포인트로 나눠 저장했다. 완료되지 않은 건만 재시도하고 Ctrl+C 시 새 작업 배정을 멈춘다. | 같은 입력·설정·출력 경로에서 재실행하면 완료 결과는 건너뛴다. 로직·입력이 바뀌면 이전 완료를 재사용하지 않도록 막는다. |
| 병렬 작업인데도 수집 속도가 낮음 | API 응답을 기다리는 동안 공용 잠금이 유지되면 다른 작업자도 대기했다. | 캐시 DB 접근만 잠그고 HTTP 응답 대기는 잠금 밖으로 옮겼다. 스레드 작업자로 I/O 요청을 겹치게 처리하면서 같은 검색어는 개별 잠금으로 중복 호출을 막았다. 요청 간격·429 cooldown·요청 예산은 공유한다. | 화면에서 완전히 보이는 구간을 재계산하면 5.05건/분 → 14.00건/분, 약 2.77배다. 통제된 벤치마크가 아니므로 전체 실행시간 단축률이나 단일 원인 효과로 단정하지 않는다. |

## 통신 개선을 설명하는 방식

이 프로젝트의 최근 개선은 HTTP 파이프라이닝을 적용한 것이 아니다. HTTP 파이프라이닝은 하나의 연결에서 이전 응답을 기다리지 않고 여러 HTTP 요청을 보내는 프로토콜 수준의 방식인데, 현재 수집기는 이를 사용하지 않는다.

구현은 Python의 `ThreadPoolExecutor`로 여러 POI 작업을 동시에 진행하는 I/O 동시성이다. 따라서 자기소개서에서는 “병렬 작업자와 비동기적인 I/O 대기 겹침” 정도로 설명할 수 있지만, 기술 면접에서는 **스레드 기반 동시 요청**, **공용 잠금 범위 축소**, **요청 속도 제한과 재개 가능성**이라고 정확히 말하는 편이 좋다. `asyncio` 기반 비동기 I/O나 HTTP/2 멀티플렉싱으로 바꾼 것은 아니다.

```text
기존
작업자 A ─ DB 잠금 ─ API 응답 대기 ─ 캐시 저장 ─ 잠금 해제
작업자 B ─────────────────────────────── 대기

변경 후
작업자 A ─ DB 캐시 확인 ─ API 응답 대기 ─ DB 저장
작업자 B ─ DB 캐시 확인 ─ API 응답 대기 ─ DB 저장
                 └ 전역 요청 간격·429 대기·호출 예산은 함께 관리
```

## 자소서용 문제 해결 문단

### 데이터 품질

> 제주 관광 POI 데이터를 통합하면서 같은 이름·주소를 가진 장소를 단순 중복으로 제거하면 ATM, AED, 화장실, 충전소처럼 기능이 다른 시설까지 사라질 수 있었습니다. 이름, 도로명·지번, 좌표 거리, 카테고리, 장소 역할을 함께 보도록 판정 규칙을 바꾸고, 애매한 후보는 자동 반영하지 않고 검토표로 분리했습니다. 또한 지도 검색 미발견을 폐업으로 단정하지 않고 행정 원천의 명시적 폐업 근거가 있을 때만 상태를 변경해 데이터 손실 위험을 줄였습니다.

### 콘텐츠 품질

> POI 설명을 빠르게 채우기 위해 장소명과 카테고리만으로 문장을 만들었지만, 장소별 특징이 사라지고 사실과 다른 표현이 생길 위험을 확인했습니다. 이후 검색, 사실 추출, 문장 생성 단계를 분리하고 상호·주소가 확인된 출처의 사실만 콘텐츠와 태그에 반영하도록 바꿨습니다. 정보가 부족한 장소는 일반 문장으로 채우지 않고 보류해, 데이터 양보다 신뢰도를 우선했습니다.

### 통신·실행 효율

> 3,234개 POI의 상세정보 수집에서 병렬 작업자를 사용해도 처리량이 낮았습니다. API 응답을 기다리는 동안 공용 잠금을 유지하는 구간을 찾아 캐시 접근과 네트워크 대기를 분리했고, 동일 검색어 중복 호출 방지, 전역 요청 간격, 429 재시도, SQLite 체크포인트를 유지했습니다. 변경 전후 실행 화면의 보이는 구간을 재계산한 결과 처리량은 분당 5.05건에서 14건으로 약 2.77배 높아졌습니다. 이 수치는 조건이 통제된 벤치마크가 아니라 관측 결과라는 한계도 함께 기록했습니다.

## 남은 검증 과제

- 실제 동일·비동일 장소 표본으로 거리·주소 규칙의 오병합과 미병합 비율을 측정한다.
- 기존 76,129행 통합 산출물에 대한 전체 콘텐츠 사실성·최신성·다른 POI 혼입 검수를 끝낸다.
- 같은 입력, workers, 캐시 조건에서 수집기를 반복 실행해 API·본문 대기, 캐시 적중, 429, 완료율, 전체 실행시간을 기록한다.
- 최신 행정 원천 수집과 Kakao 증거 갱신을 Airflow 앞단에 연결한 뒤 Asia/Seoul 스케줄과 배포 전 품질 게이트를 재검증한다.
